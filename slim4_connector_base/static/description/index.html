Slim4 Connector

Full documentation of the Slim4 connector, covering the three modules slim4_connector_base, slim4_connector_api and slim4_connector_api_inbound.

The SLIM4 connector lets Slimstock's Slim4 planning tool read Odoo's products, suppliers, stock, orders and history, and turns Slim4's order proposals into draft purchase orders in Odoo. This guide explains how to use and configure it.

What the connector does

Slim4 is always the one that starts the exchange: it pulls data from Odoo on its own schedule and pushes order proposals back. Nobody in Odoo has to export or import files.

  1. Odoo exposes products, suppliers, stock, open orders and history; Slim4 pulls them on its own schedule.
  2. Slim4 sends order proposals back; Odoo stores them as Inbound Messages.
  3. Every 5 minutes (or manually) the messages become draft RFQs.
  4. A buyer reviews and confirms them as purchase orders.

What Slim4 sends to Odoo

Order proposals: per line an article, a supplier, a quantity, an optional expected date and an optional warehouse. Odoo stores them and turns them into draft requests for quotation. Nothing is confirmed or sent to a supplier automatically.

Key concepts

Slim4 and Odoo recognise records by a few shared keys. If these keys are missing or duplicated, data is left out or orders cannot be matched.

Daily use: products and suppliers

Most of the connector runs by itself; the team's job is to keep master data complete. A product only reaches Slim4 correctly when the checklist below is met.

New product

  • Internal Reference filled in and unique (Module refuses duplicates).
  • Product is active.
  • At least one vendor line on the Purchase tab with price, minimum quantity and lead time.
  • A Primary Supplier selected on the Purchase tab, otherwise the product is missing from Logistics.
  • Slim4 Warehouses set on the Inventory tab if the product is not stocked in every warehouse.

New supplier

  • Reference filled in and unique. The module shows a Potential duplicate warning on the contact when another contact has the same reference.

Good to know

  • For variant products, only vendor lines valid for that variant (or for all variants) can be chosen.
  • Purchase prices are sent in the supplier's purchase currency, or the company currency if none is set.
  • Changes are picked up the next time Slim4 pulls data; there is nothing to trigger in Odoo.

Configuring the connector

Everything is under the Slim4 app › Configuration. The default setup works out of the box; change it only when a client needs different data in Slim4. Configuration changes require Settings (administrator) rights.

Settings

Three options, all on by default. Turn one off only if the client uses its own custom fields.

OptionWhat it adds
WarehouseSlim4 Warehouses field on products
Primary SupplierPrimary Supplier field on products
Incremental Order Quantity (IOQ)IOQ column on vendor lines

When an option is off, the fields that depend on it no longer work. Validate Mapping then reports an error until another field is chosen, and Slim4 gets an error on that data set.

Interfaces

One interface per data set (the eight listed above). Per interface you can:

  • Archive it to stop Slim4 from reading that data set.
  • Adjust Source Domain: the filter that decides which records are included (e.g. exclude a product category).
  • Review the field mapping: which Odoo value goes into each Slim4 field.

Field mapping

Each Slim4 field is one line with a status and a way to fill it.

Fields marked Required must have a value for every record; one empty value stops that whole data set for Slim4 (see Points of attention).

Buttons on the interface:

  • Validate Mapping — checks that every validated line is complete and points to an existing field.
  • Preview JSON — shows the first 5 records exactly as Slim4 would receive them. Use it after every change.
  • Reset Mapping — restores the standard configuration of that interface.

Orders from Slim4

Slim4 order proposals land in Slim4 › Inbound Messages and become draft RFQs; a buyer always reviews and confirms them in Purchase. One message is created per proposed order line.

From proposal to RFQ

  1. Slim4 sends a set of proposals (one batch). Odoo checks the whole set first; if one line is malformed (missing article, supplier or quantity, invalid date), the whole set is refused and Slim4 gets an error.
  2. Every accepted line becomes a message. Odoo looks up the article (Internal Reference), the supplier (Reference) and the receipt type of the warehouse.
  3. Lines that are found get status Received; lines with an unknown article or supplier get status Error with the reason.
  4. Every 5 minutes (or on demand) Odoo turns Received messages into draft RFQs: one RFQ per supplier and warehouse per batch, with one line per article. Price, unit and taxes come from the supplier pricelist as usual; the planned date is the date Slim4 proposed.
  5. Messages move to Processed. The buyer finds the new RFQs in Purchase and confirms them.

Message statuses

StatusMeaningWhat to do
ReceivedReady, waiting for processingNothing; or run Process Received Orders from the Action menu to process now
ProcessedRFQ createdReview the RFQ in Purchase
ErrorArticle or supplier not found, or supplier reference used by several contactsFix the product or contact, then ask Slim4 to send the proposal again (an error message cannot be reprocessed)

Automatic processing runs through the scheduled action Slim4: Process received orders. It is off after installation and must be switched on (Settings › Technical › Scheduled Actions). The list shows Received messages by default; use the filters for errors or group by batch.

Go-live checklist

Run through this list for each new client environment before Slimstock connects.

  • Internal References are unique (installation is blocked otherwise) and filled on every product to plan.
  • Supplier References are unique and agreed with Slimstock.
  • Every warehouse has a short, stable code agreed with Slimstock.
  • Primary suppliers are set on all products that Slim4 must plan (Logistics).
  • Slim4 warehouses are set on products that are not stocked everywhere.
  • Each interface reviewed with the client: statuses, source filter, Validate Mapping and Preview JSON OK.
  • An integration user for Slimstock exists, with access to products, purchase, sales and inventory and the group Slim4: Receive Inbound API Data.
  • An API key has been created for that user and handed to Slimstock together with the Odoo URL.
  • Scheduled action Slim4: Process received orders is switched on.
  • A test order from Slim4 has produced a correct draft RFQ.
  • Changes to the standard mapping are written in the mapping line Notes (a module update can reset them).

Points of attention

  1. One incomplete record blocks a whole data set. If a required value (e.g. an Internal Reference or description) is empty on one record, Slim4 gets an error for that data set until the record is fixed.
  2. One failing RFQ stops all order processing. If Odoo cannot create one RFQ (e.g. a product that cannot be purchased), none of the waiting messages are processed and the same error returns every 5 minutes. Check the scheduled action's log when messages stay Received.
  3. Error messages cannot be reprocessed. After fixing the product or supplier, Slim4 has to send the proposal again; the old error message stays as history.
  4. Warehouse codes must be text codes. A purely numeric warehouse code sent by Slim4 is not recognised, and the RFQ falls back to the default receipt type.
  5. RFQs carry no Slim4 reference. A draft RFQ does not show that it came from Slim4; the link is only visible from the inbound message.
  6. Module updates can reset mapping changes. Standard mapping lines and source filters are restored on update, including Python rules on MOQ and buying price. Keep client-specific changes documented in the line notes.
